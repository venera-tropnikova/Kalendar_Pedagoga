# MASTER RULEBOOK v2 — календарный план педагога

**Версия 2** дополняет и уточняет предыдущий свод правил результатами
независимого аудита (Codex, коммит `40684af0ec81b407a9dee548423175bf193799a6`).
Аудит проверил 26 Python-модулей приложения и 49 тестовых файлов,
собрал 730 тестовых случаев, выполнил 79 целевых тестов (PASS).
**Полный pytest не запускался, новые DOCX не создавались, повторная
визуальная проверка страниц и production smoke не проводились** — это
ограничивает уверенность в статусах ниже и должно быть закрыто отдельным
шагом, а не молчаливо считаться пройденным.

Использованы три контрольные программы:

| Программа | Недель | Всего / теория / практика |
|---|---:|---:|
| КЛЮЧ | 36 | 72 / 22 / 50 |
| Скалолазание | 36 | 72 / 11 / 61 |
| Туристы-проводники | 36 | 72 / 27 / 45 |

**Главный вывод аудита:** генератор уже умеет строить качественные
формулировки для известных конструкций, но пока **не гарантирует
сохранение смысла неизвестной программы** на всём пути
SOURCE → WEEK → TYPE → RESULT → CONTROL → DOCX. Основная проблема — не
нехватка красивых формулировок, а **молчаливое сокращение содержания**,
причём часть существующих тестов сейчас прямо закрепляет такое
сокращение как ожидаемое поведение.

## Фактическая архитектура (как есть, а не как задумано)

```
проверка файлов
  → извлечение программы/УТП
  → сопоставление (matching)
  → расписание (scheduling)
  → недельное содержание (content_generation / practice_slots)
  → CE2 (content_engine_v2)
  → lesson_resolution (может повторно менять TYPE)
  → подготовка текста ячеек (lesson_display, повторно выбирает содержание)
  → DOCX
  → структурный и визуальный QA
```

Ключевая архитектурная проблема: **выбор содержания происходит в
нескольких независимых местах** (`content_generation`, `practice_slots`,
CE2, `lesson_resolution`, `lesson_display`), и между ними нет сквозной
проверки, что все принятые элементы SOURCE дошли до нужных недель, а
TYPE/RESULT/CONTROL действительно описывают именно эти элементы. Это
не повод переписывать архитектуру CE2 — но это причина, по которой
локальные фиксы отдельных модулей не гарантируют целостность результата.

### Базовое определение полноты

Для любого правила о сохранении содержания различаются четыре типа
элементов SOURCE:

1. **обязательное действие** ученика;
2. его **объект**;
3. существенное **условие, ограничение, отрицание или альтернатива**;
4. пример, пояснение, справочный каталог (может быть законно сокращён).

RESULT не обязан дословно переписывать программу. Но исключать элемент
типа 1–3 под видом сокращения — нельзя. Если элемент не попал в
RESULT/CONTROL, это должно быть объяснимо: перенесён в другую неделю,
является пояснением (тип 4), либо не относится к проверяемому
результату. Единого механизма такого учёта сейчас нет (см. R06, R32).

### Обозначения статусов

- **IMPLEMENTED** — правило реализовано в поддерживаемом контуре и имеет автоматическую защиту.
- **PARTIAL** — реализованы отдельные случаи, но общий класс защищён не полностью.
- **MISSING** — самостоятельного механизма проверки правила нет.

`C01–C50` — предлагаемые регрессионные сценарии (раздел ниже), **ещё не
добавленные тесты**, а не уже существующая защита.

### RENDERING VARIANCE / PAGINATION QA

Разные renderer, операционные системы и доступные шрифты могут по-разному
распределять один и тот же текст по строкам и страницам. PDF-render на границе
страницы может повторить уже выведенный фрагмент текста одной ячейки таблицы.

Такое расхождение допустимо только при доказанном точном соответствии повтора
уже сопоставленному тексту той же SOURCE-cell. Подтверждённый дубль не является
новым содержанием и может быть проигнорирован matcher. Допуск не распространяется
на новый, чужой, переставленный или потерянный текст: любое такое расхождение
даёт BLOCK и обрабатывается fail-closed.

Pagination QA не должен зависеть от наличия конкретного Times New Roman,
LibreOffice или иного renderer. Обязательный инвариант — исходный текст каждой
SOURCE-cell восстанавливается из результата полностью, в исходном порядке и без
чужих вставок; renderer-specific переносы сами по себе не являются ошибкой.

## Сводка: PARTIAL (25 правил) — пять подтверждённых ограничений

**1. Компактный УТП теряет содержание ещё до CE2.**
`_first_source_sentence` сохраняет только первое предложение;
`_assign_section_blocks` из группы подтем выбирает одного представителя.
Воспроизведено: SOURCE «разминка + измерение пульса; силовые упражнения;
координация» → на неделю назначены только силовые упражнения, без
предупреждения. Существующие тесты (`test_climbing_compact_sections`)
сейчас прямо ожидают такой выбор одного представителя — это нужно
пересмотреть, а не просто «добавить правило сохранять всё».

**2. Split-head работает только для части грамматических конструкций.**
Контрпримеры: «Подготовка к соревнованиям; туристским походам» →
остаётся только «туристским походам»; «Изучение и отработка новых
приёмов; сложных элементов» → второй фрагмент теряет «отработку»;
`Проведение игр: «Первый; новых друзей»` → название разрезано пополам.
Тест на сохранение кавычек проверяет вспомогательную функцию, но не весь
путь разбиения целиком.

**3. Принцип полноты конфликтует с частью текущих эталонов.**
В существующем DOCX КЛЮЧ W20 содержание включает изготовление, игры,
экскурсию и наблюдение, но TYPE/RESULT/CONTROL сведены только к
экскурсии. В Скалолазании W28 из «Изучение голосовых команд и отработка
взаимодействия…» остаётся только отработка взаимодействия — и тест
специально требует отсутствия голосовых команд. **Вывод: нельзя просто
добавить правило «сохранять всё» — сначала нужно явно разграничить
обязательные действия и допустимо сокращаемые пояснения, сохранив уже
принятые хорошие решения**, иначе новое правило сломает то, что сейчас
работает правильно.

**4. Соответствие программы и УТП проверяется не во всех ветках.**
Если встроенный УТП не найден или его разбор завершился обычным
исключением, `resolve_utp` возвращает отдельный УТП без проверки
принадлежности программе. Воспроизведено: программа без встроенного УТП
+ отдельный УТП с чужим содержанием (страховочная система, техника
лазания, узлы) — принят без предупреждений.

**5. Pagination допускает разделение слишком высокой недели.**
Помещающиеся строки защищены от разрыва, но для чрезмерно высокой
недели предусмотрено создание нескольких физических сегментов — это
нарушает правило «одна логическая неделя = одна строка». Нужна явная
политика: не терять текст ради размещения; при невозможности безопасного
размещения — останавливать выдачу или явно запрашивать решение, а не
молча резать неделю.

## Сводка: MISSING (3 сквозных механизма)

1. **R06 — учёт происхождения и судьбы элементов SOURCE.** Нет единого
   реестра: что извлечено, куда назначено, что покрыто RESULT/CONTROL и
   почему что-либо исключено.
2. **R13 — защита логического смысла.** Нет проверки отрицаний,
   альтернатив, исполнителя действия и обязательных ограничений.
   Воспроизведено: «Выполнение упражнений без страховки запрещено» →
   «Выполняет упражнения без страховки запрещено», без единого
   предупреждения CE2.
3. **R32 — финальный смысловой quality gate.** Нынешний QA проверяет
   структуру и изображение документа, но не смысл. В копии существующего
   DOCX с искусственно очищенными TYPE/RESULT/CONTROL первой недели
   структурная проверка не вернула ошибок.

| № | Риск | Доказательство / уровень подтверждения |
|---:|---|---|
| 1 | **CRITICAL: запрет превращается в действие.** | Воспроизведён пример со страховкой; предупреждения отсутствуют. |
| 2 | **HIGH: компактный SOURCE сокращается до одного предложения или представителя.** | Подтверждено кодом, существующими тестами и отдельным прогоном. |
| 3 | **HIGH: нет финального контроля смысловой полноты.** | Нет сквозного учёта действий; структурный QA пропускает пустую триаду. |
| 4 | **HIGH: чужой УТП может миновать проверку принадлежности.** | Воспроизведено для программы без встроенного УТП. |
| 5 | **HIGH: потеря управления, составного действия и целостности названия при split.** | Три минимальных контрпримера воспроизведены. |
| 6 | **HIGH: CONTROL проверяет только часть допустимого RESULT.** | «Открытку или маску по выбору» → контроль только изготовления открытки. |
| 7 | **HIGH: содержание программы в таблицах пропускается.** | В DOCX-пробе заголовок извлечён, содержание таблицы стало пустой строкой; парсер использует `document.paragraphs`. |

предложения, нестандартные маркеры теории/практики.

### Rendering variance / pagination QA

Эти regression-кейсы обязательны и проверяются независимо от конкретного
renderer, ОС и набора шрифтов:

- точный дубль фрагмента той же SOURCE-cell на границе страницы → PASS;
- повтор слога или слова той же SOURCE-cell на границе страницы → PASS;
- посторонний текст, отсутствующий в SOURCE-cell → FAIL / BLOCK;
- потеря любого фрагмента SOURCE-cell → FAIL / BLOCK;
- перестановка исходного текста → FAIL / BLOCK.

## Governance-дополнения (не входят в аудит Codex, дополняют его)

Эти пункты не пересекаются с R01–R35 — они про роли документов, per-поле
provenance и дисциплину внесения изменений; их статус не проверялся
аудитом и должен фиксироваться отдельно.

### Роли документов
Шаблон задаёт только структуру/оформление; программа — содержание;
УТП — тематическую структуру и часы; календарь/настройки — расписание;
ранее заполненный план — только образец представления, не источник
содержания для другой программы. Неоднозначная роль файла требует
подтверждения, а не молчаливого выбора.

### Provenance по каждому полю
Независимо от статуса R06 (реестр происхождения элементов SOURCE),
каждое итоговое поле должно нести один из статусов:
**EXTRACTED** (перенесено без изменений) / **CALCULATED** (рассчитано из
подтверждённых данных) / **DERIVED** (сформулировано по методическому
правилу, со ссылкой на источник и правило) / **NEEDS_REVIEW**
(недостаточно данных или неразрешённая неоднозначность). Технические
статусы не выводятся в пользовательскую таблицу, но обязаны существовать
во внутренней модели.

### Интерфейс загрузки и проверки
Видно, какой файл загружен (полное имя); каждый файл можно удалить
независимо, без пропадания кнопок удаления у соседних; статус
«идёт проверка / завершена» заметен визуально; по итогам проверки есть
понятное пояснение, а не только внутренний лог; ошибочная загрузка (не
тот УТП, не тот год) сопровождается явным предупреждением.

### Дисциплина внесения изменений
Read-only диагностика перед любой правкой кода. Один коммит — одна
задача, в staging только файлы этой задачи. Перед коммитом — проверка
атомарности staged-состояния прогоном тестов в изоляции от остального
dirty (`git stash --keep-index`). Полный набор тестов сверяется по
числу `collected`, а не только по факту «passed» — падение числа
собранных тестов важнее любого «зелёного» итога. Изменения правил
(этого документа и PROJECT_RULES.md) коммитятся отдельно, с обязательным
показом полного diff перед фиксацией.

## RECOMMENDED NEXT STEP

**Следующий шаг — согласование смыслового контракта и тестов, а не
очередная точечная правка CE2.**

Приоритетный порядок:

1. Утвердить, какие элементы SOURCE обязательны, а какие допустимо
   сокращать. Явно разрешить противоречия с тестами, которые сейчас
   закрепляют исключение действий (см. PARTIAL-пункт 1 и 3 выше) — иначе
   исправление одного правила предсказуемо сломает другое.
2. Оформить независимые сценарии C01–C50 как исполняемые тесты; начать
   с запретов (C23–C24), потери содержания (C11–C12, C21), чужого УТП
   (C06–C08) и разбиения конструкций (C16–C20) — это покрывает
   TOP-10 риски 1, 2, 4, 5.
3. Зафиксировать уже хорошие строки трёх программ как защищённые
   эталоны, прежде чем менять общие правила — правки не должны улучшать
   один класс ценой регресса в другом.
4. Только после пунктов 1–3 исправлять механизмы по приоритету риска и
   добавить финальный gate смысловой полноты (R32).

**Архитектуру CE2 переписывать не требуется.** Но обещание «неизвестная
программа без точечных исправлений» пока преждевременно: сначала нужны
общий контракт полноты (раздел «Базовое определение полноты» выше) и его
сквозная автоматическая защита — до этого момента 25 правил остаются
PARTIAL, а не IMPLEMENTED.
