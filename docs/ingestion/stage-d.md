# Этап D: адаптер подтверждённой структуры

Изолированный модуль `calendar_pedagoga.ingestion_adapter`. База разработки:
`84b960d7e5ae75167f263d8c4002bc8a1fc7906d`. Production не импортирует адаптер;
маршрут генерации, UI и worker не подключены.

## Граница допуска

`adapt(session)` принимает Session C. До проекции он заново проверяет fingerprint,
SHA-256 исходных и преобразованных байтов и воспроизводит допустимые события C.
Требуются итоговое пользовательское подтверждение и состояние VALID. Подмена
evidence/actor или устаревшее подтверждение блокируют вход.

Источник, год, план, колонки, границы и связи берутся из подтверждённого Assessment C.
Адаптер не ищет новые планы, не разбирает склеенный текст и не сопоставляет названия.
Порядок источников и явный выбор при конфликте принадлежат C:
EXTERNAL → EMBEDDED → MANUAL. Ручной план должен быть отдельным предоставленным входом.

Выбранные UNRESOLVED, нерешённые решения разделов/фрагментов, чужой или неединственный
год, отсутствующий родитель, повтор ID или непредставленный текст блокируют адаптацию.
Явное map_columns разрешает только соответствующие роли плана, оставшиеся неясными
в исходном B; B не переписывается. Неопределённые исходные объекты вне выбранного
набора сохраняются в sidecar и получают объяснение в CoverageLedger.

## Контракт confirmed-ingestion/1

Это отдельный версионированный контракт передачи подтверждённой модели, не
переключение production PIPELINE_CONTRACT.

- AdapterPacket содержит полный неизменённый Session A+B+C, digest входа, план,
  разделы, фрагменты, связи и CoverageLedger.
- ConfirmedStudyPlanOverlay сохраняет выбранный StudyPlanCandidate, источник и год.
  Все исходные строки, четыре категории часов, точные Fraction, состояния пустых
  ячеек, итоги, ColumnMapping, evidence и арифметические проверки сохраняются.
- PlanTopic создаётся только для строк kind=TOPIC. SECTION/TOTAL и остальные
  строки остаются в canonical_plan.rows с отдельным row_provenance.
- SectionRecord и FragmentRecord содержат отдельные ContentSection и SourceFragment.
  Текст фрагмента не заменяется заголовком, не объединяется с другими фрагментами.
- Provenance содержит квалифицированный canonical ID (источник + исходный ID),
  выбранный и первоначальный year scope, SourceSpan, исходный порядок,
  родительский раздел, ID тем и ссылки на события подтверждения.
- BindingRecord сохраняет ID исходной B-связи, если она соответствует выбранной
  связи. Для новой явной связи C создаётся детерминированный ID с сохранением
  ссылок на тему, разделы, spans и журнал подтверждения.
- Один фрагмент передаётся один раз, даже если его раздел связан с несколькими
  темами. Такие темы перечисляются в topic_ids. Равный текст разных ID не схлопывается.
- parent_fragment_id и list_level сохраняются; родитель должен находиться в том же
  разделе и предшествовать вложенному фрагменту.

Нормативные таблицы, ожидаемые результаты, другие годы, невыбранные планы и
технические XML-объекты доступны в полном sidecar. Они не становятся SOURCE
активного набора и не участвуют как учебные темы.

## CoverageLedger

Одна запись на каждый source-qualified canonical ID входных A/B и материализованного
плана C. Несколько представлений одного XML-объекта перечислены в input_locations.

| Поле | Значение |
|---|---|
| ref | Источник и исходный canonical ID |
| input_locations | Все места этого ID во входном контракте |
| disposition | TRANSFERRED, EXCLUDED или BLOCKED |
| destinations | Пути в активной проекции |
| reason | Основание передачи, исключения либо блокировки |

EXCLUDED означает исключение из активной доменной проекции, а не удаление из
sidecar. Причины различают чужой год, невыбранный источник/план, ожидаемые
результаты, таблицу с её классификацией, содержание вне выбранных границ и
объекты, сохранённые только для provenance. При ошибке AdaptationError содержит
полный ledger; неполный пакет не возвращается.

## Передача UI → worker

`to_worker_json(packet)` проверяет пакет повторной чистой проекцией и сериализует
его в детерминированный JSON. Codec использует белый список dataclass-типов,
явные теги Fraction, tuple, bytes и версию контракта. Нет pickle, загрузки классов
по произвольному имени или float-преобразования часов.

`from_worker_json(payload, current_model=...)` требует текущую каноническую модель.
Digest и полная модель должны совпадать с входом пакета. После восстановления
подтверждений проекция заново сверяется целиком: изменение ID, SourceSpan,
вложенности, порядка, часов, ledger или подтверждения отвергается.

Это чистые границы передачи данных. HTTP, очередь, существующий generation worker,
распределение недель и генерация не вызываются.

## Совместимость со старыми DTO

Существующие DTO не могут без потерь выразить всю подтверждённую структуру:
ConfirmedStudyPlan поддерживает только external_utp/manual, три категории часов
и обязательные weeks/hours_per_week; старый program_overlay отвергает одинаковые
названия. Эти ограничения нельзя обходить подменой источника или текста.

Полным контрактом D является ConfirmedStudyPlanOverlay в AdapterPacket, в том числе
для встроенного плана, учебно-тренировочных часов и дробей вроде 1/3.

Две явные проекции позволяют проверить совместимость без вызова downstream:

- `legacy_content(packet)` создаёт по одному существующему ProgramContentItem
  на фрагмент и возвращает его вместе с обязательным provenance. Нельзя передавать
  результат через старый декодер, удаляя sidecar или проверяя уникальность заголовка.
- `legacy_plan(packet, ExplicitWorkload(...))` создаёт существующий ConfirmedStudyPlan
  только для точно представимых внешнего/ручного источника, нулевых тренировочных
  часов, конечных десятичных дробей и явно подтверждённой недельной нагрузки.
  Возвращается LegacyPlanBundle с исходным overlay. При несовместимости выдаётся
  CompatibilityError: нет объединения тренировочных часов с практикой, округления,
  выдуманных недель или маскировки встроенного источника под внешний.

Несовместимость legacy-проекции не является потерей канонического пакета и не
разрешает отправить его в production v1. Для встроенного источника и четырёх
категорий часов будущий потребитель должен явно поддержать версионированный
контракт; в D этот потребитель и маршрут не реализуются.

## Проверка

Тесты D проверяют идентичный JSON round-trip, отдельный Python-процесс приёмника,
полный набор canonical ID и SourceSpan, порядок, вложенность, родительские ссылки,
точные часы, сохранность решений, выбор источника, блокировки и отсутствие
production-импортов/вызовов. Структурные мутации меняют колонки, шапки, объединения,
годы, названия, вложенность и состояние подтверждений.

Реальный corpus использует один manifest, одну параметризованную функцию и один
набор инвариантов. Она проверяет все доступные ветви года/плана; неясные границы,
связи и часы не подтверждаются автоматически. Для VALID выполняется тестовое
итоговое подтверждение и полный transport round-trip. Это не пользовательская
приёмка спорного содержания документов.

PASS D: ноль необъяснённых потерь, дубликатов и межгодовых связей в адаптированном
наборе; сохранены подтверждения и provenance; неготовые входы заблокированы;
все 240 тестов A+B+C и тесты D проходят. Артефакты запуска остаются в
`_shadow_out/adapter_stage_d`, вне Git.

Этап E, production UI, переключение маршрута, RESULT/CONTROL, DOCX, push и deploy
не входят в этот этап.
